# vitest-impact Plan 1: public repo, safety fix, and the speed part

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the owner's `vitest-impact` 0.1.0 prototype into a public MIT package that runs every Vitest package of a monorepo in one process, with the selection bug fixed, and release it as `0.2.0`.

**Architecture:** The prototype already plans a selection, runs exact Vitest test specifications through the Node API, and checks plan against actual. This plan adds workspace discovery, one Vitest process with one project per package, separate processes for packages that cannot share it, shards, an isolation check, caches in the state folder, and a richer report. The selection logic stays as it is, except for the bug fix.

**Tech Stack:** TypeScript (strict, NodeNext ESM), Node 22.12+, Vitest 5.0.5 Node API (`vitest/node`), `minimatch`. The tool's own tests use Vitest.

**Spec:** `docs/design.md` (copied in Task 1). This plan covers design sections 0, 6.1, 6.3 and the version rule in section 0. Section 6.2 (records, workspace-package edges, reference-set shadow across jobs, post-merge misses) is Plan 2.

## Global Constraints

- Repo: the repo root, GitHub `vsanse/vitest-impact`, public, license MIT.
- npm name: `vitest-impact` (unscoped). Peer dependency `"vitest": "^5.0.5"`. Tested Vitest versions: `['5.0.5']`.
- `engines.node`: `"^22.12.0 || ^24.0.0 || >=26.0.0"` (unchanged).
- Runtime dependencies: `minimatch` only. Add no other runtime dependency.
- Exit codes: `0` passed, `1` test or run failure, `2` configuration error, infrastructure error, or incomplete run.
- The tool never runs a failed test again to turn it into a pass, and never changes a test timeout.
- State folder: `.vitest-impact/` at the repo root (gitignored). Caches: `.vitest-impact/cache/`.
- The tool never runs the `test` script of a workspace root.
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.
- Outward actions (create the GitHub repo, push, `npm publish`) happen only after the owner says yes in the session.

## Review Focus

1. A `--filter` token that matches no package: exit 2 with `Filter matches no package: <token>`, never a green run of fewer packages. (Task 5)
2. Two packages with the same relative test path (`test/same.test.ts`): both run, and both appear with their full repo-relative paths in the plan, report and shards. (Task 6)
3. A separate-process package that crashes before it writes its JSON report: its planned files count as missing, so the run is incomplete (exit 2). (Task 7)
4. A shard that gets no files: exit 0 with `Shard i/n has no test files.`, not the "no test files discovered" error. (Task 8)
5. A workspace root whose `test` script is `turbo test` or `pnpm -r test`: the tool never discovers or runs it, so it cannot call itself again. (Task 5)

### Task 5: Workspace discovery and `--filter`

**Files:**
- Create: `src/workspace.ts`
- Modify: `src/types.ts` (add `WorkspacePackage`)
- Test: `test/workspace.test.ts` (builds folders with `put` from `scripts/fixture.mjs` in `mkdtemp` folders)

**Interfaces:**
- Produces:
  ```ts
  export interface WorkspacePackage {
    name: string                // package.json "name"; the folder path when it has none
    dir: string                 // repo-relative POSIX folder
    kind: 'vitest' | 'script' | 'none'
    vitestConfig: string | null // repo-relative config path, when one exists
    testScript: string | null
  }
  export async function discoverPackages(root: string): Promise<WorkspacePackage[]> // sorted by dir
  export function filterPackages(packages: WorkspacePackage[], filters: string[]): WorkspacePackage[]
  ```

Rules:
- Workspace globs come from `pnpm-workspace.yaml` (only the `packages:` list; a `'!glob'` item excludes), else from root `package.json` `workspaces` (`string[]` or `{ packages: string[] }`).
- In a workspace, the root package is never a result (Review Focus 5). With no workspace, the result is the root package alone, with `dir: '.'`.
- `kind`: no `test` script → `none`. The trimmed script is exactly `vitest` or `vitest run`, and a config exists → `vitest`. Anything else (extra commands, flags, an environment prefix such as `NODE_OPTIONS=... vitest`, or no config) → `script`.
- Config lookup order: `vitest.config.{ts,mts,cts,js,mjs,cjs}`, then `vite.config.{ts,mts,cts,js,mjs,cjs}`.
- Filter tokens: a package name, or `./<glob>` matched against `dir` with `minimatch`. A `!` prefix excludes. With no positive token, start from all packages. A token that matches no package throws `Filter matches no package: <token>` (Review Focus 1). Packages of kind `none` are removed after filtering.

Behavior:
- A `vitest` unit spawns `process.execPath <vitest bin> run --reporter=default --reporter=json --outputFile.json=<outDir>/<encodeURIComponent(name)>.json --maxWorkers=<n>` in the package folder. The plan-against-actual check catches any extra file that a filter matches.
- A `script` unit runs `<packageManager> run test` in the package folder. It is always fully selected.
- Units run one at a time after the shared run, each with the whole worker budget. Add `// ponytail: separate units run one after another; run them in parallel within the budget if they dominate wall time.`
- A missing JSON file gives `files: []`, so the planned files become `missingFiles` (Review Focus 3).
- A `script` unit with `exitCode !== 0` makes the run fail (exit 1). A planned unit with no result makes the run incomplete (exit 2).
