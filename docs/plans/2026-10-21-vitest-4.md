# Vitest 4 Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** vitest-impact 0.3.0 runs on Vitest 4 (4.0.18 or later) as well as Vitest 5, in full mode and with selection.

**Architecture:** One `createVitest` call form that both majors accept. The major of each Vitest copy (the tool already groups packages by copy) decides the few options that differ: the module cache and `experimental.recordDependencies`. The tool's own suite runs twice in CI, with fixtures linked to Vitest 4.1.7 and to Vitest 5.0.5.

**Tech Stack:** TypeScript, Node 22+, Vitest 4.0.18 / 4.1.7 / 5.0.5 (targets), Vitest 5.0.5 (the tool's own test runner).

**Spec:** the owner's decision of 2026-10-21: add Vitest 4 support with selection, so a Vitest 4 repo gets the gains without an upgrade. A measurement on a 44-package Vitest 4 monorepo showed one process for all packages (Vitest 4's own `projects`) used 51% less CPU and 53% less peak memory than one process per package, but failed files that read paths relative to the package folder: the tool's parity work is still needed. `docs/design.md` stays the authority for everything else.

## Global Constraints

- Node 22.12+. ESM. No new runtime dependency.
- The tool's own runner stays Vitest 5.0.5 (`devDependencies.vitest`).
- Supported targets: Vitest `>=4.0.18 <5` and `>=5.0.5 <6`. `peerDependencies.vitest` = `^4.0.18 || ^5.0.5`.
- Never force a module cache on (ruling R31 of plan 1): the tool only points a cache that is on at its own folder.
- Exit codes unchanged: 0 pass, 1 test failure, 2 configuration, infrastructure, or incomplete run.
- Zero em dashes or en dashes in anything written. No employer, company, or private repo names anywhere.
- Commits: `Vishal Sanserwal <14056492+vsanse@users.noreply.github.com>`, each message ends with `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.

## Review Focus

1. A repo with packages on Vitest 4 AND Vitest 5 copies: one invocation, each package runs on its own copy, `sharedGroups` has one entry per copy.
2. A Vitest 4 package that turned `experimental.fsModuleCache` on in its own config: it must still run, with the same results as its own `vitest run` (the cache is speed only).
3. A separate unit (own process) on Vitest 4: its command line must not carry a flag Vitest 4 rejects.
4. Vitest 4.0.17 or older, and 6.x: exit 2 with a clear message, never a silent run.
5. Selection on Vitest 4: `related()` must find the same test files for a source change as on Vitest 5.

If a replay misses a failing file, the 4.x versions leave `TESTED_VITEST` (selection off) before release, and the miss is reported.
- G3 A PR on `vsanse/vitest-impact` for the owner's review. Publish 0.3.0 only after the owner merges.
